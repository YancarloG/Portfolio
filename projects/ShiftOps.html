Architecture notes
Why the project is structured this way.

Relational data: servers, restaurant_tables, checks, payments and incidents use IDs and relationships instead of one giant flat object.

Event-driven simulation: seating, check updates, payments and incidents generate timestamped events.

SQLite in WebAssembly: the SQL console queries a real SQLite database in the browser. The current simulation state is mirrored into SQLite whenever business data changes.

Human-in-the-loop handling: suspicious data is surfaced for review instead of silently “corrected” when intent is uncertain.

About ShiftOps
What this portfolio project demonstrates.

ShiftOps started with a simple question: what would a restaurant shift look like if I modeled it like an operations system instead of a spreadsheet?

Why a restaurant?

Restaurants naturally produce event-driven data: tables are seated, checks change, payments arrive, tips are added, and checks close. That makes the domain useful for practicing relational modeling, monitoring, SQL and operational reasoning.

Is the SQL real?

Yes. The console uses SQLite compiled to WebAssembly through sql.js. Queries run locally in the browser against the same shift data shown in the dashboards.

Is this production software?

No. It is intentionally self-contained portfolio software. The simulation replaces a real restaurant backend so the app can be opened instantly from a static site with no account or server.

What does it demonstrate?

JavaScript application state, relational data modeling, SQL, event simulation, incident workflows, dashboard design, anomaly reasoning and clear technical communication.
